# Category Icon Bug Analysis — Build 93

**Date**: 2026-09-22  
**Severity**: P2  
**Status**: Root cause identified, **ONE defect with two affected surfaces**

---

## Symptom

Two separate user reports of the same visual defect in build 93:

1. **Report ADhQB8gp** — Transaction-list filter dropdown (Activity tab): all categories display with a generic blue wallet/folder icon (📁) instead of their custom emoji.
2. **Report ACYpq1C1** — Category Trends section (Analytics tab): all categories display with a generic gray wallet/folder icon (📁) instead of their custom emoji.

**Contrast**: Category emojis render correctly in:
- Transaction list rows (left side of Activity tab)
- Category settings/picker

---

## How category icons resolve app-wide

**CategoryModel** stores the icon as `systemImage: String` (line 16 of `PersonalFinanceTraker/PersonalFinanceTraker/Models/CategoryModel.swift`), which holds either an SF Symbol string (e.g., `"fork.knife"`) or an emoji (e.g., `"🍴"`).

The app uses **two lookup paths**:

### Path A: Direct CategoryModel access (correct)
- Transaction rows and category settings read the full `CategoryModel`
- They render `categoryModel.systemImage` directly
- **Result**: correct emoji or SF Symbol

### Path B: String name → CategoryInfo lookup (broken for custom categories)
- **Location**: `CategoryInfo.info(for:)` in `PersonalFinanceTraker/PersonalFinanceTraker/Utilities/DesignTokens.swift:339–388`
- **Logic**: keyword-matches against category name and returns an SF Symbol
- Example: name contains "coffee" → returns `"cup.and.saucer.fill"`
- **Fallback**: if no keyword matches, returns `"creditcard.fill"` (generic wallet)

---

## Root cause — ONE defect, two surfaces

Both broken surfaces use **Path B (CategoryInfo keyword lookup)** instead of accessing the stored `systemImage`:

### 1. Filter dropdown: `FilterChipsView.swift:54`
```swift
Label(category.removingLeadingEmoji.localizedCategoryDisplay, 
      systemImage: CategoryInfo.info(for: category).symbol)
```
- `vm.filterCategories` is `[String]` (category names only)
- No access to `CategoryModel.systemImage`
- Falls back to `CategoryInfo` keyword match, which fails for:
  - User-created categories with no matching keyword
  - Custom emoji assignments not in the lookup table

### 2. Category Trends row: `CategoryTrendRow.swift:60`
```swift
let info = CategoryInfo.info(for: trend.category.category)
Image(systemName: info.symbol)
```
- `trend.category` is `PieChartDataPoint` (line 5 of `Features/Insights/Models/CategoryTrend.swift`)
- `PieChartDataPoint` stores only the category **name**, not the full `CategoryModel` (see `Models/PieChartDataPoint.swift`)
- Generated by `PieChartDataService.generatePieChartData()` at line 78, which does NOT include `systemImage` in the created data point
- Again falls back to `CategoryInfo` keyword match, fails for unmatched categories

**Both surfaces are cut off from the actual stored emoji because they work with aggregated/simplified data structures (String names and PieChartDataPoint) rather than the full CategoryModel.**

---

## Edge cases & constraints

1. **User-created categories**: A category named "My Custom Stuff" has no keyword match in `CategoryInfo`, so it always gets `"creditcard.fill"` (generic), even if an emoji was assigned in settings.

2. **Localization + keyword matching mismatch**: The codebase has a known related bug documented in CLAUDE.md — search matches the stored ENGLISH category key while the UI renders the LOCALISED name via `localizedCategoryDisplay` (StringEmojiExtension.swift:62–64). The icon lookup uses the localised display name (line 54, FilterChipsView), which may not match keywords designed for English keys. Example: Italian "Ristoranti e bar" contains "bar" (keyword for "bars"), but is rendered via localisation, so the match happens by accident on the Italian name.

3. **CSV import**: Imported categories inherit a `systemImage` stored on the CategoryModel, but if they're referenced only by name (as in FilterChipsView and PieChartDataPoint), the emoji is lost.

4. **Emoji vs SF Symbol**: CategoryModel can store either. The app renders them differently (emoji directly vs. `Image(systemName:)`), but only Path A surfaces handle both properly.

5. **CategoryModel deletion while transactions reference it**: Not a factor here — both surfaces iterate over active categories present in the data.

6. **Duplicate category names**: The app uses localised display names as keys, so "Transport" (English) and "Trasporto" (Italian) could theoretically collide if both seeds exist. Not observed, but categoryPersistentId lookup might be safer.

---

## Why the generic icon appears

`CategoryInfo.info(for:)` line 384 (DesignTokens.swift) is the fallback:
```swift
} else {
    symbol = "creditcard.fill"
}
```

Any category name that doesn't match one of the ~20 keyword conditions triggers this. This is rendered as a generic wallet/folder icon (SF Symbol `creditcard.fill` styled as a circular icon in both surfaces).

## Priority confirmation

**P2 is correct.**

Rationale:
- Affects two surfaces (filter dropdown, trends section), not an isolated one-off
- User-visible, affects app polish and discoverability
- Does not block task completion (categories are still selectable/visible by name)
- Shared root cause (using CategoryInfo instead of stored systemImage)

## Fix strategy (not implemented here — analysis only)

### Option 1: Use CategoryModel in both surfaces (cleanest)
- Store a reference to `CategoryModel` in `PieChartDataPoint` or a new struct
- Modify `vm.filterCategories` to expose `[CategoryModel]` not `[String]`
- Render `categoryModel.systemImage` directly (Path A)

### Option 2: Pass systemImage through aggregation (surgical fix)
- Add `systemImage: String` property to `PieChartDataPoint`
- Update `PieChartDataService.generatePieChartData()` to extract and store it from the categories parameter
- Update filter dropdown to fetch full CategoryModel from the model context and render its systemImage

### Option 3: Improve CategoryInfo fallback (weakest)
- Extend `CategoryInfo.info()` to accept an optional stored systemImage parameter
- If provided, use it; otherwise fall back to keyword matching
- Still requires plumbing systemImage through FilterChipsView and PieChartDataPoint

## Open points

1. **Why were strings used for filterCategories and PieChartDataPoint?** Design choice to simplify aggregation and avoid SwiftData model cycles? Worth documenting.

2. **Is the localization + keyword match behavior intentional?** The fix for the sibling search bug might inform this (whether to use English key or localised display name for icon lookup).

3. **How many user-created categories actually hit the fallback?** Analytics on categoryPersistentId == nil or systemImage == "creditcard.fill" would quantify impact.

4. **Should CategoryInfo keyword table expand** to cover more Italian category names (since the app UI is localised to Italian)? Current logic matches English keywords against Italian display names only by accident.

---

## Summary

**One root defect**: two surfaces render category icons via `CategoryInfo.info(for: categoryNameString)` instead of accessing the stored `CategoryModel.systemImage`. The keyword-matching fallback shows a generic wallet icon for any category without a matching keyword, including all user-created categories. Fix requires either threading the full CategoryModel through to both surfaces or adding systemImage to the intermediate data structures (PieChartDataPoint and filter category list). P2 severity is appropriate.
