# UX/UI Audit — PersonalFinanceTraker — 2026-08-03

Scope: swipe-to-delete on the Activity list, for a regular transaction vs. a recurring transaction, and the resulting recurrence-scope confirmation dialog.

## Screens audited
- Activity list, swipe-revealed delete on a **regular** transaction ("Catering") — screenshot
- Activity list, swipe-revealed delete on a **recurring** transaction ("Ricarica telefonica") — screenshot
- Recurrence-scope confirmation dialog ("This is part of a recurring series") — screenshot
- Source: `ActivityView.swift`, `EditAddTransactionView.swift`, `MainTabView.swift:58`, `DesignTokens.swift`

## Per-screen findings

### Activity list — swipe-to-delete

**Critical — Delete action uses two different colors for the identical action**
- Problem: the regular-transaction swipe button ("Catering") renders **indigo/purple**; the recurring-transaction swipe button ("Ricarica telefonica") renders **red**. Both buttons delete a transaction — same icon, same "Elimina" label, same consequence — yet they signal differently.
- Root cause (`ActivityView.swift:106-121`): the recurring branch sets `.tint(.red)` explicitly (line 113); the non-recurring branch (`role: .destructive`, lines 115-119) sets no tint, so it inherits the app-wide `.tint(Color.accentIndigo)` applied at `MainTabView.swift:58`, overriding iOS's default destructive-red for that role.
- Why it hurts UX: violates Nielsen's "consistency and standards" heuristic and the platform convention that red = destructive/irreversible. A user who has learned "purple delete button" now sees a "red delete button" for a different transaction type with no explanation for the color change — it reads as a different, more severe action, when it isn't (it's actually *less* immediately destructive, since it prompts first).
- Recommendation: add `.tint(.red)` to the non-recurring branch too (`ActivityView.swift:115`), so every delete swipe action is red regardless of recurrence. One line.

**Medium — Recurring delete no longer full-swipes, silently**
- Problem: `allowsFullSwipe: item.recurrenceRuleId == nil` (line 106) disables full-swipe-to-delete only for recurring rows, with no visual cue as to why. A user who is used to full-swipe on every other row will swipe hard, feel nothing happen, and may think the gesture failed.
- Why it hurts UX: inconsistent gesture affordance across rows in the same list breaks the "consistency and standards" heuristic and Hick's Law expectations (same gesture, different outcome, no feedback).
- Recommendation: acceptable trade-off given the confirmation requirement, but consider a subtle recurring-row indicator (e.g., a small repeat icon already used elsewhere in the row) so the differing gesture behavior has a visible cause.

### Confirmation dialog ("This is part of a recurring series")

**High — Inconsistent destructive styling between the two delete entry points**
- Problem: in `ActivityView.swift:96-101`, both `"This transaction"` and `"This and future"` are `role: .destructive` (both render red). In `EditAddTransactionView.swift:60-61`, only `"This and future"` is `role: .destructive` — `"This transaction"` has no role (renders default blue/tint).
- Why it hurts UX: the same logical choice, reached from two different entry points (swipe vs. edit-sheet toolbar), is styled two different ways. Both options actually delete data ("this transaction" alone is still a permanent delete), so the edit-sheet version under-communicates severity, while the two screens are inconsistent with each other regardless.
- Recommendation: mark both buttons `role: .destructive` in `EditAddTransactionView.swift:60` to match `ActivityView` and to correctly signal that "this transaction" is also an irreversible delete.

**Low — Dialog copy doesn't distinguish the two entry points' underlying actions**
- Problem: the dialog title/wording is identical whether triggered by "delete" (destructive) or "save" (a save-then-close-the-series flow in `EditAddTransactionView`, see `PendingRecurrenceAction.save`). A user editing a recurring transaction who taps "Save" may be surprised to see "This is part of a recurring series" phrased identically to the delete flow.
- Why it hurts UX: same dialog title used for two semantically different actions (edit-scope vs. delete-scope) can cause hesitation/misreading, especially since one path is reversible (edit) and the other isn't (delete).
- Recommendation: parameterize the dialog title/button copy by action, e.g. "Update this transaction" / "Update this and future" for the save path vs. "Delete this transaction" / "Delete this and future" for the delete path.

## Cross-screen consistency issues
- Destructive-action color (indigo vs. red) differs between regular and recurring delete swipes on the same list — see Critical finding above.
- Destructive-role assignment on "This transaction" differs between `ActivityView` and `EditAddTransactionView`'s identical-looking dialogs — see High finding above.

## Executive Summary
- **Top UX problems:** (1) delete-button color inconsistency across row types, (2) inconsistent destructive-role styling between the two confirmation dialogs, (3) unexplained full-swipe gesture difference on recurring rows.
- **Top UI problems:** indigo used for a destructive action on regular rows; dialog copy is action-agnostic ("recurring series" text reused for both save and delete).
- **Biggest accessibility issue:** none color-only-critical here (icon + text label present on both buttons), but color is the *only* signal distinguishing "this is a bigger deal" between row types, and it's backwards — the row with the confirmation step reads as more alarming (red) even though it's the safer path (asks first).
- **Biggest consistency issue:** two near-identical confirmation dialogs (edit-sheet vs. swipe) disagree on which buttons are destructive-styled.

## Quick Wins
- Add `.tint(.red)` to the non-recurring swipe button (`ActivityView.swift:115`) — 1 line.
- Change `Button("This transaction")` to `Button("This transaction", role: .destructive)` in `EditAddTransactionView.swift:60` — 1 line.

## High Impact Improvements
- Differentiate dialog title/button copy by action (delete vs. save-and-close-series) so users aren't shown identical "recurring series" phrasing for two different consequences.
- Add a small recurring-row visual indicator (repeat icon) so the disabled full-swipe behavior has a visible cause instead of feeling like a broken gesture.

## Long-term Improvements
- Extract a shared `RecurrenceScopeConfirmationDialog` view modifier used by both `ActivityView` and `EditAddTransactionView`, parameterized by action (delete/update) and scope-handlers, so the two entry points can't drift out of sync again as this pattern is reused elsewhere (e.g., a future dedicated recurring-transactions management screen).
